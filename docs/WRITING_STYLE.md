# 中文技术写作约定

写给正在准备 C++ 和量化开发面试、愿意运行代码核对结论的读者。语气接近工程师讲解代码：先回答问题，再沿着执行过程解释原因。

## 写法

- 直接陈述机制或结论。删掉为制造反转而写的“不是 X，而是 Y”“不仅……更……”；需要纠正具体误解时可以保留对比，并解释依据。
- 把抽象评价换成已有事实：哪个线程访问了什么，哪一步发生分配，哪个条件触发重试。没有证据就删去效果描述，不添加虚构测量或个人经历。
- 每段解决一个具体问题。句子顺着因果、执行顺序或例子展开，少用同构排比、口号标题、重复总结和“值得注意的是”等垫话。
- 术语保持稳定。保留 C++ 版本、平台、内存序、UB、复杂度、前提和例外；不要为求口语化模糊技术限定。
- 比较方案时写出各自的行为、成本与适用条件；操作步骤和并列条目可以用列表，其余优先使用连贯段落。
- 页面按钮直接说明动作。题目来源在作者审查材料中记录，练习界面不反复声明“非公司真题”。

## 使用规则时的判断

- 结合段落判断。某个词、标点或列表单独出现，不构成修改理由；检查它是否造成重复、空泛或误导。
- 对照句两边若分别说明了事实，或明确纠正了读者可能持有的误解，保留并写清区别。也检查拆成两句的机械反转。
- 保留有实际用途的列表、加粗与中文标点。英文标题大小写、连字符和引号习惯不直接套用到中文。
- 文体保持准确、平实。不要为制造“人味”添加情绪、故意的语病或虚构经历。

## 改写示例

原句：这不是简单的加锁，而是对并发访问边界的深刻理解。

改写：读线程持有共享锁时，其他读线程可以同时进入；写线程需要等待所有读线程释放锁。

原句：性能优化不仅要关注平均延迟，更要关注尾延迟。

改写：同时报告平均延迟和 p99、p99.9，检查慢请求是否集中在排队、缺页或锁竞争期间。

必要的纠错可以保留：`volatile` 不能建立线程间的 happens-before 关系。共享变量的同步需要使用原子操作或锁。

## 编辑流程

先标出原文的结论、证据和限定条件，再修改表达。通读相邻段落，检查是否反复使用同一种开头或结尾。最后逐项核对事实、代码、引用、链接和 frontmatter。修改专题正文后，按贡献指南完成内容复核，再更新审查 hash。
