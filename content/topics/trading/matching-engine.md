## 30 秒面试回答

撮合引擎按明确定义的规则，把订单命令转换为成交与剩余订单状态。本章采用单品种连续限价、价格优先、同价 FIFO，每笔成交按静止单价格执行；GTC 残量挂单，IOC 残量取消。实现先在候选状态计算，再一起提交内存状态和可返回的成交结果，避免异常留下半次撮合。不同交易场所和产品有不同分配规则，这个有界示例不包含持久化、账户风控或外部消息交付。

## 核心概念

来单是本次进入撮合的订单，静止单是已在簿中等待的订单。maker/taker 在这里仅用于标识这两个角色，不讨论手续费。价格时间优先先比较对来单更有利的价格，再比较同价位的接收顺序。部分成交只减少数量，未耗尽静止单继续保持原优先级。

Coinbase Exchange 的公开说明采用 price-time，并说明成交按簿中静止单价格执行；本章借此给选定规则提供具体来源，但并未实现该场所完整规则。例如其同一用户订单不能互相成交的 STP 规则需要账户身份，本例没有账户字段。[Coinbase 撮合说明](https://docs.cdp.coinbase.com/exchange/concepts/matching-engine)

CME 的公开资料列出 FIFO、Pro-Rata、含做市商分配等多种算法，还说明算法可以由多个步骤组成。因而“撮合引擎都按同价 FIFO”并不成立，讨论前必须明确场所、产品和规则版本。[CME 算法概览](https://www.cmegroup.com/education/matching-algorithm-overview)、[CME Globex 算法说明](https://cmegroupclientsite.atlassian.net/wiki/spaces/EPICSANDBOX/pages/457316046)

| 本章规则   | 精确定义                                           |
| ---------- | -------------------------------------------------- |
| 市场与类型 | 单品种、连续交易，仅限价单，无集合竞价和市价单     |
| 交叉条件   | 买限价不低于卖价；卖限价不高于买价                 |
| 选择顺序   | 买来单先最低卖价，卖来单先最高买价；同价按接收序号 |
| 成交价     | 每笔使用匹配静止单的价格                           |
| 残量       | GTC 挂单，IOC 取消，不实现 FOK                     |
| 撤单       | 仅取消仍在簿中的全部残量；未知、已成或已撤返回零   |
| 身份与范围 | ID 1..64，成功接收后本实例会话内不复用             |
| 数值与容量 | 整数 tick 价格 1..1000，数量 1..8，最多 8 张活单   |

GTC/IOC 名称对应的基本残量语义可在订单文档中核对。这里的 GTC 仅表示本实例内持续挂单，没有跨交易日或跨会话存活管理；参数边界、身份域和拒绝顺序都是本教学模型的选择。[Coinbase Time In Force](https://docs.cdp.coinbase.com/api-reference/exchange-api/rest-api/orders/create-new-order)

## 原理深入

一张买来单每次挑出价格最小且不高于自身限价的卖单。数量取两者残量的较小值，记录 maker ID、taker ID、静止单价格和本次数量，并给两边扣减相同数量。静止单归零后移除；来单归零或找不到可交叉对手时停止。卖来单将价格比较方向反转，同价顺序保持不变。

例如卖簿中先有 A：100×3，再有 B：100×4，然后 C：101×2。买来单 101×5 先与 A 成交 3，再与 B 成交 2，成交价均为 100；B 剩余 2，C 保持 2。此后买 IOC 101×7 会成交 B 的 2 和 C 的 2，并取消自己的 3。若把 A/B 顺序按数组下标而非接收顺序比较，槽位复用后就可能破坏 FIFO。

每次成功接收都必须满足：

```text
来单原数量 = 本次成交数量 + 新挂单残量 + IOC 取消残量
每张静止单原残量 = 对应成交数量 + 撮合后残量
```

还需保持活单 ID 唯一、价格与数量在域内、同价未耗尽订单优先级不变。串行执行完一条命令后，簿中的最高买价必须低于最低卖价，否则仍存在本应完成的交叉撮合。该不变量建立在本章没有特殊不可互相成交限制的规则上；加入 STP 等规则后需重新定义。

参数校验先于重复身份检查。非法价格、数量、枚举或 ID 直接拒绝；有效 ID 若曾成功接收则重复拒绝。拒绝保持正式状态不变，不返回已成交记录。成功 IOC 即使完全没成交，也属于已接收订单并消耗该 ID；容量拒绝则可在释放槽位后重试同一 ID。

## 数据结构/系统内部实现

`State` 包含 8 个固定槽位、65 项 seen 标记和已接收计数。空槽位数量为零，剩余字段一并归零。新单残量可占用任意空槽，但 FIFO 使用独立 priority；取消较早槽位不会让后来的新单排到旧单之前。最多成功接收 64 个不同 ID，所以 priority 不超过 64，没有依赖无穷递增整数或隐含回绕。

活单容量与身份容量是两件事。活单全撤后可以没有任何簿内数量，但 seen 仍保存全部已接收 ID。64 个身份用完后实例自然耗尽，必须由更高层明确新会话或身份协议；示例不会偷偷清空历史复用 ID。

每次 submit 复制 State 成为 candidate，成交写入局部固定 Result。在候选状态上完成撮合、残量处理和身份更新后，再给正式 State 赋值。状态赋值及 Result 的复制/移动由静态断言确认不抛异常，核心没有动态分配或发布回调。固定数组的元素个数由类型确定；本例元素本身都是简单值。[N4861 array](https://timsong-cpp.github.io/cppwp/n4861/array)

每轮撮合至少耗尽一张静止单或耗尽来单，因此一张来单最多产生 8 笔成交，固定结果数组足够。GTC 仅在有残量时找空槽；满簿仍可接受完全成交的来单、消耗对手单后挂残量的来单或 IOC。不能在入口只看活单数就拒绝一切。

提交前故障注入抛出专用异常，用来验证正式状态、seen 和优先级保持不变。这个保证仅针对单 owner 的内存内调用，State 赋值不是供其他线程无锁观察的原子快照。提交后外部消费者发送失败、进程崩溃或持久化失败都需要额外协议，不能依靠返回一个 Result 解决。

## 高频追问

### 回调发布一笔成交后，下一步失败怎么办？

已发送的外部事件不能靠内存回滚撤销。应先确定整条命令的提交与结果边界，再设计持久化和发布顺序。本例只构建局部 Result，正式状态提交前没有外发成交；返回后消费者失败则超出本例保证。生产设计通常还要记录可重放命令和稳定结果身份，才能判断是重新发送结果还是命令尚未提交。

### 重复 ID 拒绝等于幂等回复吗？

本例只记得身份用过，无法恢复旧请求的完整成交结果。客户端超时后重发会得到 duplicate，但仍不知道第一次具体发生了什么。可恢复幂等回复需要将身份与原始请求内容、已提交结果或可重建位置关联，明确相同身份不同内容的处理以及保留期限。

### 改单会不会丢优先级？

这取决于具体场所对改价、加量、减量和订单类型的规定。本章没有 replace，只提供新单和取消。若增加改单，必须写清哪些变化保留或更新 priority，再修改模型和测试；不能直接把数组字段覆盖当作完整业务规则。

## 容易答错的点

- “限价 101 的买单一定以 101 成交。” 本章按静止单价格执行，较优卖价可能产生价格改善。
- “IOC 要么全成要么不成。” IOC 可部分成交并取消剩余，FOK 是另一规则，本章未实现。
- “活单取消后 ID 就能重用。” 活单移除与去重历史独立，本模型的身份保留整个有限会话。
- “8 个槽满了就直接拒绝。” 撮合可能不需要挂单或释放槽位，需按候选结果判断。
- “固定数组赋值完成就保证结果不会丢。” 这里只保证函数内状态与可返回结果一致，不提供崩溃恢复或网络交付保证。

## 性能分析

设活单容量为 N，一次挑选最优对手扫描 N 个槽，最多成交 N 张单，因此参数化最坏撮合复杂度为 O(N²)，复制候选、找空位及撤单为 O(N)。本例 N 固定为 8，边界便于审查，但不能据此宣称生产规模的 O(1) 撮合。每次结果还要产生 k 笔成交，至少有 O(k) 的结果工作。

慢 oracle 将数量展开为单位，最多 64 个静止单位，排序与逐单位删除有额外成本，专门用于交叉验证。它的执行时间不能代表撮合核心。生产中可采用价格索引、档内 FIFO、ID 索引和预分配节点，代价是多个结构必须一起维护；容量、异常和结果缓冲不足的策略也要同时设计。

性能测试应分别覆盖空簿挂单、同价深队列、多档扫单、取消突发和满容量压力，记录每条命令的成交笔数。吞吐以相同业务工作量比较，并明确延迟从网络入口、序列器还是撮合开始算，是否包含结果排队和持久化。消费者变慢可能让结果队列成为限制，核心函数快并不意味着端到端 p99/p99.9 低。

本章只有有限功能检查，没有固定 CPU、预热、重复计时或采集原始分布，因此没有纳秒级延迟、吞吐或加速比结论。若替换数据结构，先保留规则与 oracle，再比较成本，不能为了降低计时删除拒绝、恢复或溢出检查。

## Quant/Low-Latency 场景

单 owner 撮合线程可以串行执行权威命令序列，使同价 FIFO 和撤单顺序可重放。多入口线程需要明确谁决定这个序列；各自本地时间不能自然组成一致的接收全序。将网络输入、前置风控、序列器、撮合与结果消费者连接起来时，还要定义队列满后的背压或拒绝行为。

模拟撮合用于策略回放时，输入行情重建和模拟成交规则也要区分。市场数据中的可见数量未必包含隐藏单或真实排队位置，用本章 price-time 模型得出的成交结果只能对应设定的假设。它不构成对真实成交概率或收益的证明。

扩展到实际交易系统之前，需要具体规则版本、账户与风险状态、STP、价格带、停牌或竞价状态，以及日志和恢复协议。Coinbase 文档中的 STP 和 CME 的多步骤分配展示了会改变成交结果的规则差异；本例没有把这些场所规则拼成一个所谓通用引擎。
