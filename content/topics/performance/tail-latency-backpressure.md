## 30 秒面试回答

尾延迟描述分布中较慢的一部分请求。请求即使只需要很短的服务时间，也可能在突发、慢消费者或下游停顿后排很久。背压让上游感知处理能力，配合有界队列和准入策略限制积压；排队可能因此转移到客户端，测量时仍要计算这段等待。报告分位数必须带样本量、负载模型和拒绝、超时比例，否则成功请求看起来变快，整体服务却可能更差。

## 核心概念

先固定一次请求的时间边界。以下符号用于本例成功请求：到达 `a`，开始服务 `s`，完成 `f`。排队时间 `s-a`，服务时间 `f-s`，端到端延迟 `f-a`。实际 RPC 的端到端范围可能还包含客户端准入等待、网络和响应返回，不能直接把服务器内计时当成用户体验。

| 量或机制 | 本章含义                     | 容易遗漏的条件                 |
| -------- | ---------------------------- | ------------------------------ |
| offered  | 计划进入模型的全部请求       | 包括拒绝与超时                 |
| admitted | 获准开始或进入等待队列       | 不等于最终成功                 |
| 等待容量 | 仅限 FIFO 中尚未开始的请求数 | 服务槽独立，容量零仍可直接服务 |
| 背压     | 限制上游继续提交的反馈       | 需要找到等待最终存放的位置     |
| 负载丢弃 | 在无法接受时明确拒绝工作     | 拒绝也有成本，结果要进入统计   |
| deadline | 从原始到达开始的完成预算     | 超时不保证后台立即停止         |

本例把等待容量满时拒绝新请求作为准入策略，没有实现阻塞上游的 API。闭环轨迹只表示一个串行客户端的反馈行为。将两者称为同一种背压实现，会掩盖实际等待发生的位置。

限流约束允许提交的速率或并发量；拒绝给当前请求一个不接受的结果；取消要求已经接受工作的执行方尽量停止后续操作。背压则需要让上游知道下游暂时无法继续接收，例如接收方发放 credit，或在高水位暂停提交、低水位恢复。上游仍要限制待提交数据和等待时间，credit 归还、关闭唤醒及恢复条件都属于协议的一部分，不能仅用一个满队列返回值替代。

分位数使用 nearest-rank：升序样本数为 `N`，百分位 `p` 对应第 `ceil(pN/100)` 项，一基计数，`N=0` 时结果不存在。成功条件分布只包含成功请求；其旁边必须列出全部 offered 的结果分类。拒绝通常很快，不能把它作为低延迟成功样本。

## 原理深入

考虑单个非抢占服务器。第一个请求占用 5 个 tick，后续请求各占用 1 个 tick，每 tick 有一个新请求到达。即使后续服务速度恢复，已经形成的队列也需要时间处理。如果长期有效到达工作量超过可用处理能力，扩大队列只能延后触及容量上限；如果只是有限突发，空闲阶段可能将积压排空。平均到达率低于平均服务能力也不排除短时等待，服务成本的分布和相关停顿仍会影响尾部。

Little 定律在相应稳定性和长期均值条件下联系平均在途量 `L`、流率 `λ` 与平均停留时间 `W`：`L=λW`。使用它要先选定同一边界、同一请求群体。比如只计算准入队列，流率就不能用包括拒绝的 offered 速率；请求已超时而后台仍执行时，客户端终结与资源释放的停留时间也不同。原论文摘要明确列出有限均值、平稳性等条件，这个平均关系不能直接计算 p99，也不能不加检查地套入持续增长的积压。[Little 原论文](https://pubsonline.informs.org/doi/10.1287/opre.9.3.383)

开放负载按计划继续产生到达，闭环负载会因等待响应而降低提交速率。当目标行为是开放到达，测量器却在系统停顿时也停止发送，只计实际发出请求的往返时间，就可能出现 coordinated omission：原本应在这段时间到达的请求及其等待没有进入样本。闭环适合真实串行用户行为，但其分布不能直接代表独立到达的需求。wrk2 因此将延迟与预定发送时刻联系起来；实际测试还要确认生成器能达到设定负载，并记录计划与实际提交的偏差。[wrk2 的测量说明](https://github.com/giltene/wrk2)

端到端截止预算应扣除已经发生的等待，再向下游传播。跨主机时钟没有共同绝对原点，通常由框架传播剩余时长并扣除已消耗时间。截止到达后，等待方的结果可以先终结，工作线程却仍需收到取消并在安全位置停止。本例刻意保留超时工作，直到服务时间耗尽，以暴露这部分资源占用。[gRPC deadline 与取消责任](https://grpc.io/docs/guides/deadlines/)

## 数据结构/系统内部实现

模型为每个请求保留 `arrival`、`service`、`deadline`、结果以及可选的 `start`、`work_done`。`terminal` 是对调用方产生完成、拒绝或超时结果的时刻。一个 `active` 槽承载非抢占工作，`deque` 保存等待请求编号。超时的 active 保持占用，后续工作完成时只填写 `work_done`，不能把结果改回成功；排队中的请求过期则立即移出队列。

事件时钟只跳到下一次到达、完成或尚未终结请求的截止时刻。同一 tick 按以下顺序处理：

1. 完成运行中的工作；若尚未超时，将结果设为成功。
2. 终结截止已到的运行请求，并移除过期等待者。
3. 服务器空闲时先启动最早的旧等待者。
4. 按输入顺序处理这一 tick 的新到达；零预算直接超时，其他请求按服务槽和等待容量决定准入。

这一定义让恰好截止时完成的请求成功，也让恰好截止但尚未开始的请求超时。它是教学模型的边界约定，真实 API 可能有不同的超时竞争规则，需要按实际契约解释。

不变量包括：等待数不超过容量，每个请求只有一个最终结果，运行中的请求最多一个，所有开始过的工作在模拟结束时都有完成时刻。输入请求数与等待容量各不超过 256，到达必须非递减，服务时间严格大于零。时间相加先检查 `uint64_t` 剩余空间；最大可表示 tick 本身仍是合法时刻，没有被借作无事件哨兵。模型处理有限轨迹，不加入自动重试，也不宣称真实系统能在固定墙钟时间内完成这些工作。

截止测试中，第 0 条在 tick 2 超时，工作到 tick 5 才停止，输出 `queue=0 service_work=5 e2e_to_outcome=2`。因此超时行不满足成功路径上的“排队加服务等于端到端”关系。未开始的超时请求将等待直到超时的时间记入 `queue`，服务消耗为零。即时拒绝的三个时长都是零，仍单列为拒绝。

## 高频追问

### 服务率足够，为什么突发仍使延迟增加？

服务能力是在时间上逐步兑现的。空闲时未使用的处理时间不能储存起来抵消未来所有突发；多个请求同时到达，仍需争用有限服务槽。判断队列是否合适，要观察请求成本和突发长度，以及积压在下一次突发前能否排空。单一长期 QPS 会丢失这种时间结构。

### HdrHistogram 能自动修复所有遗漏吗？

它能在配置范围和精度内保存计数分布，也提供按预期采样间隔补充遗漏记录的机制。补充依赖所选间隔和负载假设，不能恢复未真正执行请求的业务结果，更不能替代拒绝、超时和负载生成器滞后的记录。合并总体分布应合并兼容的计数，不能平均各实例的 p99。[HdrHistogram 文档](https://github.com/HdrHistogram/HdrHistogram)

### 队列满后 sleep 再重试就算背压了吗？

先检查重试者在哪里保存请求、最多多少个、等待是否计入 deadline。若只是把有界服务队列外扩成无限客户端任务列表，资源问题仍在。重试也会增加处理成本；多层各自重试可能放大请求量，需要共同的尝试预算和剩余时间，退避与抖动只能调节时序，不能保证持续过载恢复。[Google SRE 的过载处理](https://sre.google/sre-book/handling-overload/)

## 容易答错的点

- p99 必须说明群体、窗口和样本数；低成功 p99 可以与高超时率同时出现。
- 排队上限按请求数定义时不能自动限制字节和 CPU 成本，异质请求需额外预算。
- 阻塞生产者可能把等待移到调用线程或上游队列，端到端计时不能从解除阻塞后才开始。
- 超时不会撤销已经提交的远端业务；重试之前需处理结果未知和重复执行。
- 各阶段 p99 不能直接相加得到端到端 p99，阶段间的相关性和请求配对会影响分布。
- 有界准入限制本地积压；当服务能否完成本身无上界时，它不能单独提供严格延迟上界。

## 性能分析

示例是小规模事件模拟器。设请求数为 `N`、最大等待数为 `Q`，下一事件选择会扫描等待队列，过期移除也有移动成本；整个模拟可按 `O(N(Q+1))` 上界理解，保留记录和队列用 `O(N+Q)` 空间。分位数函数复制并排序成功样本，成本 `O(N log N)`，没有声称适合直接放在交易热路径。

真实测量需要记录计划到达、实际提交、各阶段排队与完成，并明确跨进程时间戳如何关联。控制请求大小和服务成本分布，分别测试平稳到达、突发、消费者变慢及恢复阶段。记录生成器是否达到目标到达率，报告吞吐、队列年龄、占用字节、完成和失败率，以及有足够样本支持的 p50、p99、p99.9。保留重复实验和原始分布，说明计时器、机器配置、线程放置与观测开销。

增加队列容量、批处理或并行度都可能改变吞吐和等待：批处理等待更多输入，扩大并行度可能争用缓存、锁或下游配额。应在相同 offered 轨迹和业务成本下比较，同时检查是否只把超时转成拒绝，或把积压转到另一个组件。大规模请求依赖也会让个别慢分支进入端到端尾部，这类问题需要在完整调用路径观察。[The Tail at Scale](https://research.google/pubs/the-tail-at-scale/)

## Quant/Low-Latency 场景

行情分发中的慢消费者可以积累大量旧数据。若消费的是允许覆盖的最新状态，可以按标的合并；若是依赖连续序列的增量，任意丢弃会破坏状态，需要断开、恢复或重同步协议。为每个消费者设置资源上限和数据年龄限制，可以避免一个迟缓连接占满全局内存，但是否可暂停上游读取还取决于同一链路承载的其他流量。

订单入口应在还未承担执行责任时明确拒绝无法准时处理的请求，并保留业务身份。已经提交到外部会话却超时的订单可能仍被执行，不能用本地 deadline 推断“未下单”。取消和重试要遵循业务确认与幂等规则，避免过载时增加重复风险。

停机或故障恢复阶段也需要背压。恢复流量与实时流量共用线程、存储或下游配额时，可以分别设置准入预算，并观察实时请求的队列年龄和恢复进度。优先级策略需要防止低优先级长期饿死，也要把被拒绝的恢复工作保存在有界、可追踪的位置。
